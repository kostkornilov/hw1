# Homework 1

## GPU и версии ПО

- GPU: NVIDIA Tesla T4, 16 GB; использовалась одна GPU (`cuda:0`).
- Python: 3.12.13.
- PyTorch: 2.10.0+cu128.
- CUDA: 12.8.
- Режим: FP32, `eval()` и `torch.inference_mode()`.
- `cudnn.benchmark`, cuDNN TF32 и matmul TF32 отключены.

## Воспроизведение

1. Создать или открыть Notebook в Kaggle.
2. В `Session options` выбрать ускоритель GPU T4 x2.
3. Запустить сессию.
4. Открыть `Run → Kaggle Jupyter Server`.
5. В разделе `Manually Connect an Existing Notebook` скопировать VS Code Compatible URL (если вы запускаете код в колабе -- Colabe compatable URL, там процедура похожа).
6. Локально открыть `measure.ipynb` в VS Code.
7. Нажать `Select Kernel` в правом верхнем углу ноутбука.
8. Выбрать `Existing Jupyter Server → Enter the URL of the running Jupyter server` и вставить скопированный URL.
9. После подключения запустить все ячейки.

Для подключения в VS Code должны быть установлены расширения Python и Jupyter. Код ноутбука остаётся в локальном файле, а ячейки выполняются на Kaggle Jupyter Server.

Ноутбук сохраняет измерения в `results/measurements.csv`, найденные параметры в `results/theta.json`, а графики — в `results/figures/`. Повторный запуск продолжает измерения из существующего CSV и не создаёт дубликаты конфигураций.

## Results summary

Были измерены все 132 конфигурации. Параметры latency и energy калибровались на 63 точках основной сетки. Остальные 69 конфигураций, содержащие хотя бы одно случайно выбранное значение `image_size` или `batch`, использовались как validation. Это выбранное нами разбиение, поскольку задание не задаёт его явно.

Параметры latency подбирались на основной сетке функцией `scipy.optimize.least_squares` с минимизацией относительной ошибки; оптимизация в логарифмическом пространстве сохраняла параметры положительными. Затем latency-модель фиксировалась, поскольку её prediction входит в формулу энергии, и неотрицательные energy-коэффициенты подбирались функцией `scipy.optimize.lsq_linear`. Validation-точки ни на одном этапе калибровки не использовались.

| Метрика | Train | Validation |
|---|---:|---:|
| Latency MAPE | 17.9% | 20.2% |
| Latency RMSE | 34.2 ms | 37.7 ms |
| Energy MAPE | 17.1% | 19.9% |

Полученные параметры калибровки:

Аналитическое число FLOPs близко к результатам `torch.profiler`. Для памяти наибольшие относительные расхождения наблюдаются при малых размерах изображения; при больших `S` аналитическая и измеренная зависимости ближе. Ни одна конфигурация не завершилась с OOM. Максимальная аналитическая оценка памяти на исследованной сетке составляет 6.50 GiB при `S=512`, `B=256`, что меньше 16 GB памяти Tesla T4.

## One-page discussion

Аналитическая формула FLOPs хорошо воспроизводит измеренную зависимость, поскольку размеры тензоров и число операций свёрточных и линейных слоёв определяются однозначно. Небольшое расхождение возможно из-за Global Average Pooling и других операций, FLOPs которых profiler может учитывать иначе.

Модель памяти хуже описывает конфигурации с малым `S`. Формула содержит постоянное слагаемое `4P ≈ 3.97 MiB`, соответствующее весам, а также аналитическую сумму входа и активаций всех слоёв. Однако `torch.cuda.max_memory_allocated()` измеряет максимум одновременно выделенной памяти. В последовательной сети промежуточные тензоры имеют разное время жизни, а CUDA-операции могут использовать временные рабочие буферы. При малых активациях даже небольшое абсолютное расхождение даёт большую относительную ошибку. При увеличении `S` начинает доминировать слагаемое, пропорциональное `BS²`, поэтому модель лучше передаёт наблюдаемый рост памяти. Это расхождение связано с допущениями аналитической модели, а не с fitted-коэффициентами: функция памяти не калибруется по измерениям.

Отчётливого перехода между memory-bound и compute-bound режимами на графике полной latency обнаружить не удалось. При больших изображениях измеренная latency растёт с batch size примерно линейно и следует общей форме предсказания. Модель использует одну эффективную пропускную способность и одну вычислительную производительность для всей сети, хотя отдельные свёртки, pooling и активации имеют разную арифметическую интенсивность. Их переходы между режимами складываются в общее время forward pass и могут выглядеть как плавная кривая. Дополнительно на малых конфигурациях заметны время запуска CUDA-ядер, неполная загрузка GPU и вариативность измерений. Для прямого определения режима каждого слоя потребовался бы layer-wise profiling.

Для используемого FP32-режима теоретическая пороговая интенсивность Tesla T4 составляет около 25–27 FLOP/byte: согласно спецификации NVIDIA, GPU имеет 8.1 TFLOP/s FP32 и 300–320 GB/s пропускной способности памяти. Fitted bandwidth 70.2 GB/s составляет около 22–23% пиковой, а fitted throughput 2.96 TFLOP/s — около 37% пиковой FP32-производительности. Это эффективные параметры всей сети, а не прямые аппаратные измерения: разные формы тензоров, накладные расходы запуска ядер и неполная загрузка GPU снижают достигаемую производительность. У fitted-модели порог `pi / beta` равен примерно 42.18 FLOP/byte, а аналитическая интенсивность сети приближается к пределу 48.66 FLOP/byte. Поэтому fitted-модель допускает compute-dominated режим для крупных конфигураций. Увеличение batch size выше 256 почти не повысит интенсивность, поскольку она уже близка к своему пределу.

Ошибки energy на train и validation близки, поэтому заметного ухудшения на ранее невиданных координатах сетки нет. При этом energy-модель сводит поведение всей GPU к idle power, числу FLOPs и bytes moved. Найденный коэффициент энергии на byte практически равен нулю. Это не означает, что передача данных физически не потребляет энергию: признаки latency, FLOPs и bytes moved сильно связаны на данной сетке, поэтому калибровка не может надёжно разделить их вклады. Модель также не учитывает фоновую активность GPU и различное энергопотребление отдельных операций, поэтому её параметры следует рассматривать как эффективные коэффициенты для данного запуска.

OOM на заданной сетке не наблюдался: максимальная аналитическая оценка составила 6.50 GiB, что меньше 16 GB памяти T4. Поэтому эксперимент не определяет фактическую границу OOM. OOM связан с доступным объёмом памяти и отличается от memory-bound режима, который связан с пропускной способностью памяти.
